# ADR 004: Human-in-the-loop feedback pipeline

**Context**

TLA Advisor was built for an environment with limited existing documentation. The building-specific knowledge base was sparse at the start, and the expectation was that it would grow over time as staff encountered and resolved issues. The question was how new knowledge should enter the system — and who should control that process.

**Options considered**

- Auto-ingest user corrections directly into the vector store — fast, but no quality control. A single bad or malicious correction could corrupt the knowledge base.
- Admin-only ingestion — only admins can add documents. Safe but creates a bottleneck and loses the on-the-ground knowledge that frontline staff accumulate.
- Human-in-the-loop pipeline — staff submit corrections, a regulariser model validates and formats them, an admin approves or rejects, approved corrections are ingested into the vector store.

**Decision**

User corrections go through three stages before entering the knowledge base. First, a regulariser LLM validates the correction — filtering out vague, off-topic, or injection-attempt submissions and reformatting valid ones into a consistent structure. Second, the formatted correction sits in a pending queue for admin review. Third, on approval, the correction is chunked, embedded, and added to the vector store. Approved corrections are also written to a Samba-mounted file on a shared Linux system — a business requirement agreed with the project manager to maintain a human-readable record of all accepted knowledge additions independent of the vector store.

**Consequences**

- The knowledge base can only be corrupted by a correction that passes both the regulariser and a human reviewer — two independent checks
- The Samba write gives a persistent, auditable record of what knowledge has been accepted into the system
- The regulariser stage reduces admin review burden by filtering low-quality submissions before they reach the queue
- The pipeline adds latency to the correction flow — a user's correction does not immediately improve the system, it waits for admin approval
- The system was ultimately not deployed due to maintenance concerns after the original developer's departure from the institution
