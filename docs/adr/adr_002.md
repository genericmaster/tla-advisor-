# ADR 002: Composition root at startup

**Context**

TLA Advisor depends on three model clients — an embedding model, a generator, and a regulariser — plus a vector store client and the RAG pipeline that connects them. The question was when and where these should be constructed.

**Options considered**

- Construct components per request — clean isolation but rebuilds the entire pipeline on every query, including client connections and dependency wiring
- Lazy initialisation — construct on first use, cache after. Adds conditional logic throughout the codebase and still pays the construction cost on the first request
- Composition root at startup — construct everything once when the app starts, share across all requests

**Decision**

`start_up.py` acts as the composition root. When FastAPI imports it, Python executes the module top to bottom — the Ollama client, embedder, vector store, generator, regulariser, and the full `RAGPipeline` are all instantiated immediately. By the time the first request arrives, the entire system is assembled and ready. Every request calls `pipeline.answer()` on an already-wired system.

**Consequences**

- No per-request construction overhead — the pipeline is always available
- The Ollama client stays connected across requests rather than reconnecting each time
- Model weights stay warm in Ollama's memory after first use — `start_up.py` doesn't load the weights itself, but by keeping the client alive it avoids the cold-start penalty Ollama applies when a model hasn't been called recently
- Startup is slower — the app isn't ready until everything is initialised, which is an acceptable tradeoff for a single-instance internal tool
