# ADR 003: Dependency injection for pipeline components

**Context**

The RAG pipeline needs three operations to function — embedding, retrieval, and generation. The question was whether these should be created inside the pipeline or passed into it from outside.

**Options considered**

- Create dependencies inside `RAGPipeline` — simpler upfront, but the pipeline now owns the construction logic for its dependencies. Changing the embedding model or generator means changing the pipeline class itself.
- Inject dependencies from outside — the pipeline receives already-constructed components and only concerns itself with orchestration.

**Decision**

`RAGPipeline` receives its `embedder`, `vector_store`, and `generator` as constructor arguments — it never creates them. The same applies to `OllamaGenerator` receiving a pre-built `Client` rather than creating its own. All construction happens in `start_up.py` and is passed in.

**Consequences**

- Each component can grow independently without touching the pipeline. In a separate branch, a vision capability was added by extending `OllamaGenerator` with a vision function — the `RAGPipeline` required no changes
- Swapping a component means changing `start_up.py` only — the pipeline is indifferent to which concrete implementation it receives, as long as it satisfies the abstract interface
- The pipeline's only job is orchestration — it coordinates the steps but owns none of the logic of any individual step
- The tradeoff is that wiring complexity moves to `start_up.py`, which becomes the one place that needs to understand how everything fits together
