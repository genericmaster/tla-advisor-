# ADR 001: Abstract interfaces for pipeline components

**Context**

The RAG pipeline depends on three external services — an embedding model, a vector store, and a generator. The question was how to structure those dependencies so the system can grow without the components becoming tangled.

**Options considered**

- Call ChromaDB and Ollama directly throughout the pipeline — ends up as a monolith where all components are coupled together, making it impossible to extend or replace one without touching everything else
- Abstract base classes for each component — each component has a defined contract, concrete implementations are wired at startup, and the pipeline only talks to the abstraction

**Decision**

Abstract base classes (`Embedder`, `VectorStore`, `Generator`) with concrete implementations wired at startup. The pipeline never talks to ChromaDB or Ollama directly — only to the abstractions. This gives control over what gets added or removed from each provider's API without the rest of the system caring.

**Consequences**

- Swapping a provider means writing a new concrete class and changing one line in startup
- The abstraction layer gives control over how each provider's API is exposed to the rest of the system
- Discovered that abstract classes are still coupled to the API shape of the provider underneath — cross-provider swaps with very different APIs require more thought than just a new subclass
- The system is currently coupled to Ollama as the inference provider — the abstract interface helps at the code level but doesn't fully solve inference provider extensibility; future work needs to think more carefully about how to make the system genuinely portable across different inference providers
