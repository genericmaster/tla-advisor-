# ADR 005: Factory pattern for document loaders

**Context**

The ingestion pipeline needs to handle multiple document types — PDFs, text files, and potentially others in future. The question was how to route an incoming file to the correct loading logic without the rest of the pipeline needing to know what type of file it is dealing with.

**Options considered**

- Separate functions per file type — straightforward but every new file type requires a new function and a new import everywhere it's needed. Any change ripples through the codebase.
- One class per file type, called manually — same problem. The caller has to know which class to instantiate based on the file type, which means the routing logic is scattered across the codebase.
- Factory pattern — one function that receives a file path, determines the type, and returns the correct loader instance. The rest of the pipeline only ever talks to the factory.

**Decision**

`get_loader` in `loader_factory.py` acts as the factory. It inspects the file extension and returns the appropriate `DocumentLoader` subclass — `PDFLoader`, `TxtLoader`, or `StringLoader`. The ingestion pipeline calls `get_loader(source)` and receives a loader without knowing or caring which concrete class it gets back. Adding a new file type means adding one new class and one new condition in the factory — nothing else changes.

**Consequences**

- The ingestion pipeline and the upload endpoint are decoupled from document type specifics — they only interface with the factory
- Adding a new file type is isolated to one place
- The factory is simple — an if/elif chain — which is honest for the current number of supported types. A more sophisticated registry pattern would be warranted if the number of types grows significantly
- Acknowledged limitation: the current implementation could be structured more cleanly; the factory pattern is sound but the execution has room for improvement
